# goroutine 为什么这么轻？线程与 goroutine 的底层对决

> 这是 [《Go 并发四件套：goroutine、channel、interface、select》](/posts/go-goroutine-channel-interface-select/) 的深度姊妹篇（**草稿**）。
> 主文章里只说"goroutine 很轻"，这篇从**操作系统内核**和 **Go 运行时**两个层面，把"轻"背后的机制讲透：
> 线程的上下文切换为什么贵？goroutine 的切换为什么便宜？栈为什么能动态增长？调度器凭什么能扛百万并发？

---

## 0. 先看结论：两三个数量级的差距

| 对比项 | 操作系统线程 | goroutine |
|---|---|---|
| 初始栈大小 | 1~8 MB（创建时固定分配） | **2 KB（按需动态增长）** |
| 创建成本 | `clone()` 系统调用，内核参与，约 10µs 级 | 纯用户态分配结构体，约 100ns 级 |
| 切换成本 | 陷入内核，约 1~2µs，且缓存全凉 | 用户态寄存器保存/恢复，约几十 ns |
| 切换方式 | 内核抢占式调度（CFS） | 运行时协作 + 异步抢占 |
| 单进程数量级 | 几千个就吃力 | **几十万到百万没问题** |

差距不是"一点点"，而是**两三个数量级**。下面从底层看差距从哪来。

---

## 1. 线程的代价藏在哪

操作系统线程是**内核管理的调度实体**，每一步都很贵：

### 1.1 创建：clone() 系统调用

`pthread_create` 最终走 `clone()` 系统调用。内核要为它分配：

- task_struct（进程/线程描述符）
- 内核栈
- **8MB 虚拟地址空间的用户栈**（Linux 默认 `ulimit -s` = 8192KB）

创建成本约 10µs 级——**每次进入内核都是一次特权级切换**（用户态 ↔ 内核态），加上内核里的各种链表操作和资源分配。

### 1.2 切换：内核上下文切换五步走

线程 A 切到线程 B，内核要做的事：

1. **陷入内核态**（用户态 → 内核态，特权级切换）
2. 把 A 的全部寄存器现场保存到 A 的内核栈
3. 切到 B 的内核栈，恢复 B 的寄存器现场
4. **切换页表基址（CR3）→ TLB 全部失效** → 之后一段时间所有内存访问都 miss，CPU 缓存也是冷的
5. 回到用户态，从 B 的断点继续

一次切换 1~2µs，**加上缓存冷却的隐性代价，实际开销还要翻几倍**。所以"千级线程"就能把 CPU 耗在切换上——大量时间花在"换人"而不是"干活"。

### 1.3 内存：8MB 一次性锁死

每个线程的 8MB 栈是**创建时一次性分配的虚拟地址空间**——哪怕只用 1KB 也占着 8MB。1000 个线程 = 8GB 虚拟内存，物理内存按需触页但虚拟空间先炸。这是"线程数量上不去"的硬天花板之一。

## 2. goroutine 的底层：g 结构体 + 用户态切换

Go 运行时里，每个 goroutine 对应一个 `g` 结构体（`runtime/runtime2.go`），关键字段：

```go
type g struct {
    stack       stack      // goroutine 自己的栈区间 [lo, hi)，初始只有 2KB
    stackguard0 uintptr    // 栈增长检查点（下文第 3 节）
    sched       gobuf      // 切换时寄存器的"存档点"
    ...
}

type gobuf struct {
    sp   uintptr   // 栈指针（rsp）
    pc   uintptr   // 程序计数器（rip）
    g    guintptr  // 属于哪个 goroutine
    ...
}
```

### 2.1 创建：不碰内核

`go` 关键字只是让运行时在堆上分配一个 `g` 结构体 + 2KB 栈，放进队列——**不碰内核**，约 100ns。对比线程创建的 10µs，快了两个数量级。

### 2.2 切换：函数调用级的跳转

goroutine 阻塞时（等 channel、`time.Sleep`、系统调用），运行时用一段汇编（`asm_amd64.s` 的 `gogo`）把当前寄存器**存档到 `g.sched`**，再从下一个 goroutine 的 `g.sched` **恢复寄存器**：

- 不陷入内核（没有特权级切换）
- 不碰页表（TLB 还是热的）
- 不碰 CPU 缓存（缓存是热的）

本质上就是一次"函数调用级的跳转"，几十纳秒搞定。

### 2.3 一个形象的类比

- 线程切换 = 换一个**员工**：要重新办入职、换工位、清空桌面（内核态全套流程）
- goroutine 切换 = 同一个员工**换个活干**：只需要把手里的笔放下、拿起另一份图纸（保存/恢复寄存器）

## 3. 栈怎么"动态增长"（copystack）

2KB 栈不够用了怎么办？Go 的做法是**换一个更大的栈，把内容搬过去**：

1. 每个函数入口都有栈检查：`rsp` 低于 `stackguard0` 就触发 `morestack`
2. 运行时分配一个更大的栈（2KB → 4KB → 8KB…指数增长，上限 1GB）
3. **把旧栈内容整体复制到新栈**，并修正栈上的指针
4. 旧栈回收

为什么"搬栈"是安全的？因为 Go 有**精确垃圾回收（precise GC）**，能准确找到栈上所有指针，移动栈后把所有指针修正到新位置即可——这在 C/C++ 里根本做不到（无法枚举栈上的指针）。

> 历史小知识：Go 1.3 之前用的是"分段栈"（segmented stacks），栈满就挂一个新段。缺点是有"栈分裂"（hot split）问题：循环里反复触发的增长/收缩会抖动。Go 1.3 换成连续栈 + 复制方案，彻底解决。

## 4. 调度对比：GMP vs 内核 CFS

| | 内核调度器（CFS） | Go 运行时调度器（GMP） |
|---|---|---|
| 调度对象 | 线程（内核眼里只有线程） | goroutine |
| 就绪队列 | 每 CPU 一个红黑树 | 每个 P 一个本地队列 + 全局队列 |
| 抢占 | 时钟中断强制抢占 | 协作点挂起 + Go 1.14 起信号异步抢占 |
| 并行上限 | 与 CPU 核数无关 | **GOMAXPROCS = 可并行运行的 goroutine 数** |

GMP 三个字母：

- **G** = goroutine（干活的人）
- **M** = 操作系统线程（工位，真正的执行者）
- **P** = 处理器（调度器，每个 P 管一个本地 goroutine 队列）

### 4.1 关键机制一：M 阻塞，P 不闲

当 goroutine 发起系统调用导致 M 阻塞，调度器把 P 连同它的本地队列**交给其他空闲 M**，继续跑别的 goroutine——这就是"阻塞不占工位"的底层实现。

### 4.2 关键机制二：netpoller，连 M 都不用阻塞

网络 IO 走 `netpoller`（Linux 上是 epoll）：goroutine 发起网络读写时注册进 epoll 就挂起，**M 完全不被占用**。数据到了由 epoll 唤醒对应 goroutine。这就是为什么"十万个网络连接"对 Go 来说稀松平常。

### 4.3 关键机制三：异步抢占（Go 1.14+）

一个 goroutine 死循环不退出怎么办？Go 1.14 引入基于信号的**异步抢占**：运行时会向占用 P 过久的 M 发送信号（SIGURG），强制打断当前 goroutine，防止"一个毒 goroutine 饿死所有人"。（1.14 之前只能靠协作点让出，死循环确实会饿死别人。）

### 4.4 关键机制四：work stealing

P 的本地队列空了，会去**偷**其他 P 队列尾部的 goroutine（以及其他 M 的），保证所有 CPU 核都忙起来，负载自动均衡。

---

## 5. 总结

| 层面 | 线程 | goroutine |
|---|---|---|
| 创建 | 内核参与，10µs 级 | 用户态，100ns 级 |
| 切换 | 内核态 5 步，1~2µs + 缓存全凉 | 寄存器存档/恢复，几十 ns |
| 栈 | 8MB 固定 | 2KB 起，copystack 动态增长 |
| 调度 | 内核 CFS | 用户态 GMP + work stealing |
| 阻塞 | 占着内核线程 | 让出 P，M 不闲（syscall）/ M 都不占（netpoller） |

**一句话**：线程把"并发"的成本交给了内核，goroutine 把成本留在了用户态——这就是 Go 能撑起百万并发的全部秘密。
